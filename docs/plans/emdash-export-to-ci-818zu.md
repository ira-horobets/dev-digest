## Verified GitHub facts (researcher, 2026-10-31)
- **Permission headers.** `X-Accepted-GitHub-Permissions` (format `contents=read`, comma-separated; alternatives separated by `;`) is documented only for fine-grained PATs and GitHub Apps on "Resource not accessible by …" errors. Classic PATs get `X-OAuth-Scopes` / `X-Accepted-OAuth-Scopes` instead. A bare 404 is not a permission signal. → D5, rows 3, 4, 13, 21, 22. Source: https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api
- **Fine-grained permissions per operation.**
  - Create a ref, or write contents under `.github/workflows/`: Contents write + Workflows write (classic: `repo` + `workflow`).
  - Create a PR: Pull requests write.
  - List repo and org secrets (`/repos/{o}/{r}/actions/organization-secrets`): Secrets read (classic: `repo`).
  - List workflow runs and download artifacts: Actions read (classic: `repo`).

  → `PERMISSION_TABLE` (row 10), D5. Sources: https://docs.github.com/en/rest/overview/permissions-required-for-fine-grained-personal-access-tokens, https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps, https://docs.github.com/en/rest/actions/secrets
- **Workflow permissions.** `pull-requests: write` alone allows PR reviews and PR conversation comments (`POST /repos/{o}/{r}/issues/{n}/comments`). → D9. Source: https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions#permissions
- **Reviews from `GITHUB_TOKEN`.** Only `APPROVE` is documented as blocked by the repo setting "Allow GitHub Actions to create and approve pull requests". `REQUEST_CHANGES` via `GITHUB_TOKEN` is not officially documented either way. → D12 fallback, rows 33, 45, 54. Source: https://github.blog/changelog/2022-05-03-github-actions-prevent-github-actions-from-creating-and-approving-pull-requests/
- **Artifact download.** `GET /repos/{o}/{r}/actions/artifacts/{id}/{format}` answers 302 with a URL on a different origin that expires after 1 minute. Follow it immediately, without the `Authorization` header. `size_in_bytes` is in the artifact list, so the size can be checked before download. → row 4. Source: https://docs.github.com/en/rest/actions/artifacts

## Risks & open questions
- The ESM bundle plus `node .devdigest/runner/index.js` relies on Node 22 module-syntax detection when the target repo has no `"type"` in `package.json`, and fails in a repo that declares `"type": "commonjs"` at the root. Mitigation: the workflow pins Node 22 via `setup-node`. If this proves unreliable, the fallback (a plan amendment, not a spec change) is a runner step that copies the file to `$RUNNER_TEMP/devdigest-runner.mjs` and runs that with `node`.
- D12 rests on undocumented behaviour (`REQUEST_CHANGES` from `GITHUB_TOKEN`). The fallback (row 33) keeps the check result correct either way. The only visible difference is a COMMENT review or a PR comment instead of "Changes requested".
- Memory churn: because memory is part of the hash (AC-38), adding any memory row marks every installation of that repo out of date. This is the spec's behaviour; review may flag it as noisy.
- `commitFiles` catches any `getRef` error as "branch missing" (`octokit.ts:302-309`). A 403 on the branch read would try `createRef`, which then fails with GitHub's reason. That is acceptable: it never writes to the base.
- `withRetry` around `commitFiles` can add one extra commit on a retried timeout. EC-2 allows "one more commit at most".
- The committed bundle goes stale whenever `reviewer-core/src` or the shared contracts change, including through worktree A's merges. The stale-bundle test and `.github/workflows/agent-runner.yml` catch it. Whoever merges last rebuilds `dist/index.js`.
- `insight.sh`, `verify.sh` and `route.sh` do not know `agent-runner/`. Insights for it go to the root or `reviewer-core` INSIGHTS until the tooling is re-vendored.

## Decisions taken by default
- D1 Skill file slug = `slugify(skill.name)` (ci-local copy of the skills algorithm), with `-2`, `-3` suffixes on collision in link order. The agent manifest slug = `slugify(agent.name)`. Skills included = enabled links to enabled skills, in link order (the set local reviews use).
- D2 `CiExportInput.triggers` default `['opened','synchronize']`, `min(1)`. `base` removed. New `workflow` and `confirm_overwrite`. All new shapes stay in `eval-ci.ts`.
- D3 Default branch read live via `GitHubClient.getRepoInfo` at export and update. `findOpenPr` / `openPullRequest` also return `number`.
- D4 The client validates YAML (`yaml`) and builds the zip (`fflate`). The server parses the edited workflow again on export.
- D5 (verified) Naming the missing permission, in this order:
  1. Fine-grained PAT / App: parse `X-Accepted-GitHub-Permissions` (`;`-separated alternatives of `,`-separated `name=level`) and phrase it as "Workflows: write".
  2. Classic PAT: `X-Accepted-OAuth-Scopes` minus `X-OAuth-Scopes`, phrased as "`workflow` scope".
  3. When neither header names it, use the `PERMISSION_TABLE` fallback for a 403 on that operation, phrased per token kind:
     - commit / ref under `.github/workflows/` → Contents write + Workflows write (classic: `repo` + `workflow`)
     - open PR → Pull requests write
     - list secrets → Secrets read (classic: `repo`)
     - list runs / download artifact → Actions read (classic: `repo`)

  A bare 404 never names a permission: GitHub's reason is shown with "not found, or the token cannot see it".
- D6 The runner imports `server/src/adapters/git/diff-parser.ts` by relative path into its bundle. `reviewer-core` is unchanged.
- D7 Stepper, option card, file viewer and status badge live in `client/src/components/<kebab>/` and go on `/showcase`. Not a design-system task.
- D8 Secret state: in the repo list or the org list → `ready`. Repo list read, org list read or `null` because of no org (404 on a user repo), not found, and the repo has no environments → `not_set`. Otherwise (403, network, rate limit, org list unreadable, environments exist) → `unknown` with the reason.
- D9 (verified) Workflow `permissions`: `github_review` and `pr_comment` → `contents: read`, `pull-requests: write`. `none` → `contents: read`, `pull-requests: read`. The optional `contents: read`-only variant for `none` was not taken, because the runner reads the PR and its diff through the pulls API, which needs `pull-requests: read` on private repos.
- D10 Ingest mapping: `ci_runs.status` from the GitHub conclusion + artifact findings (AC-62). `agent_runs.status` = `done` when the artifact is valid, else `failed`. `ran_at` = the run's `created_at`. `ci_runs.duration_ms` = `updated_at − run_started_at` from GitHub. `agent_runs.duration_ms` = artifact `duration_ms`. PR number = the first of the run's `pull_requests`, else the artifact `pr_number` (fork PRs report none). Provider `openrouter`, model from the artifact.
- D11 AC-48 is read for a completed review: the exit code equals the gate. AC-51 and any error before the review completes exit 2 without an artifact; the CI run is then ingested as `failed`.
- D12 (undocumented behaviour, with a fallback) The runner posts `REQUEST_CHANGES` when the gate trips and `COMMENT` otherwise. It never sends `APPROVE`, which is documented as blocked for `GITHUB_TOKEN` unless the repo allows it. `REQUEST_CHANGES` from `GITHUB_TOKEN` is not officially documented, so:
  - a review rejected with 403/422 is retried once as a `COMMENT` review;
  - if that is rejected too, the runner posts one PR comment with the same body;
  - the exit code stays `gate ? 1 : 0` in every case.

  The Configure step shows a hint under "GitHub review" that repo Actions settings may reject reviews (rows 33, 45, 54, 60).
- D13 `ci_runs` rows whose installation was deleted (`ci_installation_id` set null, EC-20) are not listed, because no workspace scope remains. Their `agent_runs` rows stay with `agent_id` null.
- D14 The runner bundle is read by `platform/runner-bundle.ts` (pattern `platform/prompts.ts`) instead of a container getter. Amendment 2: `platform/container.ts` does get one `ciRepo` getter, because `routes-no-persistence` forbids `ci/routes.ts` from constructing the repository; it is an additive hunk shared with worktree A.
